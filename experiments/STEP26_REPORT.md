完整证据：[JSONL 原始轨迹](results/step26-2026-09-23.jsonl)（约 2.0 MB，281 行）和[可重新生成的逐段摘要](results/step26-2026-09-23-summary.json)。轨迹含一次性初始化、15 个预热样本、252 个正式样本、每段起止读数及一条标记的延迟样本。结果均在非 App Sandbox 的普通用户宿主权限下取得。

## A–D. 修复的缺陷与时间、资源生命周期

1. 旧版 GPU 功率、DCS 流量率和 Python 摘要按配置间隔归一化。现在每个 IOReport 订阅保存前一个计数样本与 `CLOCK_MONOTONIC` 时间戳，速率使用同组两个采样调用之间的 `window_s`。CPU tick 和 VM swap 页计数也各自保存基线与时间戳。非正窗口无效；超过 `max(30 秒, 10×配置周期)` 的 IOReport 窗口标记 `stale` 并重建基线。采样失败会丢弃原基线，恢复后的第一个成功样本只建立新基线。计时器在实际完成后安排下一次采样，不追赶遗漏周期。`nominal_interval_s` 仅描述调度，不用于速率。
2. 旧版 `cpuRead` 和 `vmRead` 每次调用 `mach_host_self()`。现在启动时获取一次，采样全程复用，退出时 `mach_port_deallocate`。`host_processor_info` 返回的 Mach 分配数组在正常及异常计数路径均 `vm_deallocate`。`host_statistics64` 使用调用方栈上的结构体，无返回数组需要释放。
3. 旧版只有 `main` 的自动释放池；现在每次采样都有独立 `@autoreleasepool`。相同的加速公开指标诊断中，600 次采样后的 RSS 从 8.60 MB 上升并停在约 9.14 MB；旧版同类测试从 8.60 MB 持续增至 11.62 MB。加速诊断用于检查生命周期，不作为常规开销基准。
4. `public,memory` 同时启用时只读取一次 `HOST_VM_INFO64`。物理内存总量、拓扑、GPU DVFS 表、IOReport 通道和 SMC 键元信息均在初始化或首次成功读取时缓存。JSON 序列化失败现在使进程非零退出，避免悄然丢行。

## E–F. 通道与拓扑有效性

- GPU 只接受唯一的 `GPUPH`，单位必须是 `24Mticks`，状态必须恰有 `OFF` 与 `P1`–`P15`，且不能重复或出现负驻留。已观察到的非零状态须能映射至本机 DVFS 表；输出的是全机活跃率及活动期间的状态加权频率，后者标为 `estimated`。
- 功率只把唯一 `GPU Energy`、`nJ` 差分转为估算瓦数；拒绝负值、非有限值及高于 1000 W 的明显异常。CPU Energy、DRAM0 和 ANE0 保留原始诊断值，但状态为 `unavailable`，不生成有效的 0 W 功率。不会叠加可能重叠的供电轨。
- DCS 后端保留 63 个诊断通道。派生 GFX 流量只接受各唯一的 `GFX DCS RD/WR`、`B`、非负值，用本组实际窗口归一化；`v01_approved=false`。这次没有做可选的带宽口径验证，因此不能由该数值推算带宽余量。
- 启动时同时检查芯片名 `Apple M1 Max`、10 核、perflevel 8 P／2 E 和 `IODeviceTree:/cpus` 的逐核 `logical-cpu-id`／`cluster-type`。全部吻合才启用 P/E 分组。临时诊断编译故意使芯片名不匹配，实测总 CPU 仍为 `measured`，P/E 均为 `unavailable` 且值为 `null`。该诊断未改动仓库源码。

所有样本保留 `status`、来源和相应单位／窗口。无数据用 `null`，不以数字零替代。AppleSMC 温度是具名传感器读数，不声称为封装最高温。

## J–M. RSS、端口、延迟与质量

- 预热阶段 RSS 为 11,943,936→12,173,312 B。正式段 0 早期升至 12,189,696 B，段 2 有一次 16,384 B 台阶升至 12,206,080 B。其余段均保持平台，特别是最后两段和段 3 的所有样本保持同一 RSS。最大观测 RSS 为 12,206,080 B；未取得独立的进程历史峰值。没有与样本数持续相关的增长证据。
- 预热和正式样本中的 host-port 发送权引用数**全部为 2**；每个段边界同为 2。每次用 `proc_listchildpids` 检查，子进程数全部为 0。这是实际进程查询，不是常量声明。
- 注入样本的 tick 窗口为 **6.217753 s**，GPU Energy 窗口为 **6.217003 s**，DCS 窗口为 **6.216988 s**。对应 GPU 估算功率 **0.2200 W**、GFX 流量 **2.1993 GB/s**；邻近样本分别约 0.21–0.23 W 和 1.93–2.22 GB/s。下一次 tick 窗口恢复 **2.0114 s**，无快速补采。该延迟小于显式 30 秒 stale 阈值，所以正确按完整实际窗口归一化。
- 252 个正式样本的 CPU、VM、swap 占用、swap 活动、当前压力、两个温度键、GPU、功率和带宽组均为 `measured`。**失败 0、invalid 0、stale 0、重建基线 0**。原始 GPU nJ 差分和 GFX 字节差分对派生速率的独立复算误差为 0。未人为触发硬件读失败或计数器重置，因此恢复路径只有静态代码审查，没有动态故障注入证据。

## N–O. 节奏与进入下一步的判断

**建议 v0.1 的 CPU／GPU 活跃率／GPU 频率使用约 2 秒快节奏。**三段 2 秒测试均低于单核 0.37%，时间窗口与延迟稳定，注入延迟能恢复；5 秒显著减少定时唤醒和自身 CPU 时间，但会放慢快速负载变化的反馈。温度、VM 分类、swap 和私有 DCS 诊断可以考虑约 5 秒或更慢的独立节奏，热状态与压力变化可使用通知；本次实验为保守地测量完整组合，在每个周期均读取所有这些指标，未实测拆分节奏的最终产品开销。

**Step 3 无剩余的测量有效性阻塞项。**私有 IOReport/SMC 的系统升级兼容性和非沙箱分发前提仍在；能力探测失败必须降级为不可用。GFX DCS 的物理口径验证仍是其进入 v0.1 的独立前提；本次实验没有执行该可选实验。真实 ML 训练吞吐及最终 UI 能耗不在本次实验范围内。12 分钟平台期支持轻量常驻采集的下一步开发，但不是跨系统版本或多日连续运行保证。
